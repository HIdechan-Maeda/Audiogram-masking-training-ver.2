# AGENTS.md — teaching/ ディレクトリの作業規約

Nagami Lab（北海道医療大学 言語聴覚療法学科）の AudioScope EDU 教材開発における規約。
このディレクトリで作業する AI エージェント（Cursor / Claude Code など）は以下に従うこと。

---

## 1. 最優先事項

### 学術的正確性
- 文献・数値・事実には出典を明示する。
- **存在しない文献を作り出さない。** 著者名・雑誌名・巻号頁・DOI を推測で埋めない。
- 確認できていないことは「未確認」と明記する。曖昧にぼかさない。
- 統計や研究方法に言及するときは、前提条件と限界を必ず書く。

### 個人情報を書かない
- 患者・研究参加者の氏名、カルテ情報、生年月日、施設内の識別子をこのリポジトリに入れない。
- 症例はすべてプログラムが生成した合成データ、または教材用に創作した架空の人物である。
- 実在の症例を下敷きにする場合でも、識別可能な情報は残さない。

### 教育用設定値と臨床基準を区別する
本教材の数値の多くは**教育用の設定値**であり、臨床の診断基準ではない。両者を混同した記述は誤りとして扱う。

教育用設定値の例：両耳間減衰量 50 dB、安全域 10 dB、DPOAE の SNR 判定 6 dB、
アブミ骨筋反射が消失する ABG の目安 10〜15 dB、各聴力像パターンの最小 ABG・付与確率。

これらを書くときは「本課題の設定値」「教育用の設定」と明示する。文献により幅がある場合は
「単一の基準として確定していない」と書く。学生に暗記させる数値として扱わない。

## 3. 単一の情報源の原則

症例の生成条件（`generation` 節）は、AudioScope EDU の生成器と課題シートの両方がこの
JSON から読む。**EDU 側で条件を別途ハードコードしない。** 条件がずれると、学生が画面で
測った聴力像と、手元のシートに印刷された条件が食い違い、教材として破綻する。

同様に、マスキングの式は `build/masking.mjs` にだけ置く。学生シートに印刷される式も
教員用の正答も、すべてここから導出される。式を 2 箇所に書かない。

`representativeThresholds` は教員用の代表値であり、`seed` を変更したら
`build/sync-thresholds.mjs` で必ず再同期する。手で書き換えたまま放置しない。

## 4. 教材設計の原則

新しい症例を作るとき、以下を崩さない。

**段階提示（S1〜S6）。** 学生は先の情報を見ずに進む。各段階で予測を書かせ、次の段階で
照合させる。予測欄を空のまま進める構成にしない。

**他覚的検査を先、自覚的検査を後。** 純音聴力検査を最初に出すと、骨導を知った状態で
他の検査を解釈する確認作業になり、推論が発生しない。症例1では DPOAE（S3）を
純音聴力検査（S4）より前に置いている。この順序には理由があるので、安易に戻さない。

**検査間の整合を必ず問う。** 4検査そろった教材の存在理由がここにある。「矛盾はあるか、
ないならなぜ矛盾しないか」を各症例で問う。ルーブリックでもこの軸を最重視する。

**レベル構成。** レベル1は整合の型を学ぶ。レベル2は鑑別する。レベル3は矛盾を検出する
（非器質性難聴、後迷路性病変、手技エラー）。

**年齢の制約。** 生成システムの検証グリッドは 20〜70 歳代で、18歳未満は対象外。
小児に多い疾患でも成人症例として設定し、その旨を教員用に補足する。

## 5. 実装状況について断定しない

AudioScope EDU の以下は**未確認**である。断定的に書かず、教員用の「要確認事項」に残すこと。

- 4検査が同一症例IDで連動生成されるか（技術論文 v2.32 で出力規則の適合を検証したのは
  純音聴力検査の生成部分のみ。ティンパノ・反射・DPOAE との検査間整合は未検証）
- 段階提示（検査ごとの解禁）が UI で可能か
- マスキング量に応じた閾値変化（シャドー聴取、オーバーマスキング）が実装されているか
- アブミ骨筋反射の非交叉・交叉を分けて提示できるか
- DPOAE が DP-gram（周波数別 SNR）で表示できるか

`cases/index.mjs` の `toGeneratorOptions()` は `src/engine/generateAudiogram.js` の
API（sex: Male/Female、出力 right/left 行配列）に合わせて正規化する。

## 6. docx 生成の落とし穴

過去に踏んで修正済み。同じ轍を踏まないこと。

- **同じ罫線設定の段落を連続させない。** Word / LibreOffice が 1 つの枠として結合し、
  罫線が 1 本しか描かれない。記入用の罫線は `lines()` のようにテーブルで作る。
- **改ページに `PageBreak` 段落を使わない。** 直前の要素がページ末に乗ったときに
  空ページが生まれる。見出しの `pageBreakBefore` を使う（`h2(title, { newPage: true })`）。
- **テーブルは `columnWidths` と各セルの `width` を両方 DXA で指定する。**
  パーセント指定は Google Docs で崩れる。列幅の合計を本文幅 9020 に合わせる。
- **セルの網掛けは `ShadingType.CLEAR`。** `SOLID` は黒く潰れる。
- 日本語フォントは `Yu Gothic` を既定にしている。

## 7. 生成物の検証

docx を変更したら、必ずレンダリングして目視で確認する。

```bash
node build/build.mjs case01
cd dist
soffice --headless --convert-to pdf *.docx
pdftoppm -jpeg -r 80 case01_臨床推論課題_学生用.pdf s
# s-*.jpg を開いて確認する
```

特に確認すること：空ページが出ていないか、記入罫線が本数どおり描かれているか、
表がページ途中で分断されていないか、設問の見出しと記入欄が離れていないか。

## 8. 言語と文体

- 日本語で書く。専門用語・コード・識別子は原文のまま。
- 教員用は常体（である調）、学生用は敬体（ですます調）で統一する。
- 学生用の設問文に答えを混ぜない。誘導しない。
- 教員用には「なぜその設計か」を書く。手順だけでは他の教員が引き継げない。
